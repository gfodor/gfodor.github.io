The Document

An engine without a save subsystem — the runtime model and the file on disk are the same bytes, kept that way by one MutationObserver and a ten-second timer.

Source: webspace-sdk/webspace-engine · src/systems/, src/utils/ · master @ 2026-05-24 · MPL-2.0

Premise§ 1

Most engines have a save function. The user clicks Save; the engine walks its in-memory scene graph; each entity is serialized into JSON, into a binary blob, into a database row. The file on disk and the runtime model are two representations of the same state, kept in sync by traversal — a function called serialize, with a counterpart called deserialize. The two functions exist precisely because the two representations are different.

The webspace engine does not have these functions.

The cast§ 2

We follow Alice. She has just dragged a model duck two meters east in her browser. The duck is a tag in her HTML document — a <model id="abc1234" src="assets/duck.glb"> sitting as a direct child of <body>. Before she dragged it, its style attribute read transform: translate3d(0, 50cm, 0). After she dragged it, the attribute will, in 250 milliseconds, read transform: translate3d(220cm, 100cm, -50cm). That string is the change.

The engine's job, between the moment Alice releases the mouse and the moment a second user — Bob, opening the same world tomorrow — sees the duck in its new position, is to: write that string into the DOM, observe that the DOM has changed, base64-encode the document, push it to GitHub. That is the entire save subsystem.

The flush · 250 ms§ 3

The system that does the writing is DomSerializeSystem. It runs at sixty frames a second. Every frame it scans the entities it has been told to watch — every <model>, <img>, <video> with a matching A-Frame entity. For each, it polls a flag the renderer sets when the entity's world matrix has been modified. If the flag is set, the entity is added to a flush queue and a 250-millisecond timer is started.

When the timer fires — which is when Alice has not moved the duck for a quarter second — the queue is drained. For each pending entity, the system reads its current matrix, decomposes it into position, rotation, and scale, formats those into a CSS transform string, and writes that string into the style attribute of the entity's DOM element via setAttributeIfChanged. There is no model layer being updated. The DOM is the model layer.

The observer§ 4

In another file, a single MutationObserver has been waiting. It was registered against document.documentElement with everything turned on: subtree, childList, attributes, characterData. It has been firing for every mutation in the document since the page loaded.

Most of those mutations are noise. A React UI library called styled-components inserts and removes <style> tags in the head as components mount and unmount; the observer's callback walks each MutationRecord and discards records whose only removed nodes are styled-components <style> elements. Every other mutation — including Alice's style write on the <model> — sets a single flag: documentIsDirty = true.

Ten seconds§ 5

The same callback that sets the dirty flag also schedules a timeout, ten seconds out: setTimeout(write, MAX_WRITE_RATE_MS). Every subsequent mutation cancels the previous timeout and reschedules. So as long as Alice keeps moving things, no save happens. The moment she stops — really stops, for ten consecutive seconds — the timer fires and the write begins.

The whole save subsystem is a debounce.

The write§ 6

What write() does is what its name suggests, with no ceremony. It reads document.documentElement.outerHTML — the entire HTML document as a string. It runs three GitHub REST calls in sequence: create a blob containing the HTML bytes; create a tree referencing the blob in place of the old index.html; create a commit pointing at the tree, parented to the current branch tip. It updates the branch reference to the new commit.

There is no diff, no patch format, no schema migration. The whole file becomes a new whole file. The browser is the editor; the GitHub repository is the filesystem; the commit is the save.

The document, both times§ 7 · climax

What just happened is worth pausing on. There was no save function called. There was no walk of a scene graph. There was no serialization of an in-memory model into a format. The duck's new position was not persisted to anywhere — it was already there, the moment the style attribute changed. The DOM is the model. The DOM is the file. The two are not representations of the same state kept in sync; they are the same bytes, separated by an HTTP request and a base64 step.

There is no save function. There is only the document, and a ten-second timer.

The webspace engine is not above or below the document. The webspace engine is what runs while the document is being mutated, and the save is what happens when the document stops being mutated for ten seconds. That is the entire architecture, and it explains a great deal about the rest of the codebase. Most of the systems in src/systems/ are not, on closer reading, about managing world state. They are about mutating the DOM correctly — and about reacting when someone else does so first.

Bob, the next morning§ 8

Bob opens his browser to the same URL. The browser fetches the HTML file from GitHub Pages. The browser parses the HTML — the way browsers always have, since 1993. Webspace's WorldImporter runs immediately after, iterates the children of <body>, and for each one with a recognizable tag and a seven-character id, creates an A-Frame entity.

For Alice's duck, it finds the <model id="abc1234">, reads transform: translate3d(220cm, 100cm, -50cm) from style, runs parseTransformIntoThree to convert that string into a Vector3, a Quaternion, and a scale, and sets the entity's matrix accordingly. There is no load function beyond parse the file the browser already parsed. The 3D model spawns at the right position because the position was always in the file — it was a CSS transform string sitting in an HTML attribute.

Reveal · the old position. The architecture treats reliability as the user's problem: the debounce trades latency for save fidelity, and if the user kills the tab during the window, nothing commits. The document-dirty-state-changed event exists precisely so the UI can warn before unload — but the warning is the engine's only line of defense. There is no last-second flush.

The honest version§ 10

It is worth being precise about what this architecture is and is not. If Alice and Bob are in the same world at the same time, with a live presence connection between their browsers, Bob does not see Alice's drag through the GitHub commit. He sees it over a WebRTC data channel, via a separate network protocol (NAF, Networked A-Frame) that updates his entity's transform every frame. The DOM mutation, the ten-second timer, the GitHub commit — those are for persistence. They are how the world survives Alice closing her browser. Real-time sync is a different layer with different code.

The architectural choice the webspace engine made is selective. It uses DOM-as-source-of-truth for everything that must survive a reload, and NAF for everything that must arrive in twenty milliseconds. The two stories are easy to confuse.

There is one place the two stories meet, and it is worth a margin note. When a peer changes a hub-level setting — the sky color, the spawn point, the permission list — the change does not ride NAF. It is broadcast as an update_hub_meta message, which the receiving client routes through pushHubMetaUpdateIntoDOM. That function does not modify any in-memory model. It modifies the DOM — specifically, it adds, removes, or updates <meta name="webspace.environment.terrain.colors.sky"> tags in <head>. A second MutationObserver, this one watching <head>, fires. It dispatches a hub_meta_refresh event. Every subsystem subscribed to that event — the atmosphere shader, the sky-beam renderer, the spawn-point indicator — updates. Local and remote hub-metadata changes converge at exactly the same line of code: an append on a <meta> tag. The DOM is, for this slice of state, the event bus.

There are four MutationObservers in the entire codebase. Two of them are the persistence pair just named (documentElement, head). The other two are scoped helpers — pauseAllPlayableElements on <body> for media auto-pause, and CursorTargettingSystem on <a-scene> for raycast-cache invalidation. The architectural cleverness lives in two of the four. The grand framing of "everything is observed" is romantic but inaccurate; the precise framing is "what must survive a reload is observed, and survives by being part of the document."

Reveal · the hub-meta observer. atom-metadata.js:75 watches <head> for webspace.* meta-tag mutations; any change fires hub_meta_refresh, which fans out to atmosphere, sky, spawn-point, and permission subscribers. The other three options use direct event channels or props — they are conventional pub/sub. Only the hub-meta path replicates the document-as-substrate pattern. The A-Frame componentchanged path is the trap: it looks like the pattern but it is a direct emitter on the entity, not a substrate observation.

webspace-engine · src/systems/ overview

In summary · review queue · § 13

Webspace-engine elides the boundary between runtime model and save file. The DOM is both. To save the world, the engine waits ten seconds and pushes the document to GitHub. To load it, the engine asks the browser to parse it. The ‘engine’ is the system that runs while the document is being mutated and that knows when to stop mutating long enough to commit. There is no in-memory scene graph behind the scenes. There are no serialize and deserialize functions. There is the document. Most of the code in src/systems/ is not, on closer reading, about managing world state; it is about mutating the DOM correctly — and about reacting when someone else does so first. The architectural cleverness lives in two of the codebase’s four MutationObservers, both of which fit inside a single screen of source.
